## 共識與實作

- 私有 `quiz_student_identity()` 只從 `auth.uid()`、已確認信箱、115 學年名冊與三／六年級班碼核對。目錄、葉片、錯題功能不再為取得年級而重算整份選卷清單；不開放前端直接呼叫。
- 選卷進度一次彙整本人作答，再連接試卷，保留空白卷的零題進度。
- 組卷先彙整本人各題的歷次作答次數，再供候選排序查表，避免每抽一題、每個候選都重新查答案表。保留未做過優先、題數、難度、補題、種子與去重規則。排序次數以該次組卷開始的快照為準；同帳號另一分頁同時送答，下一次組卷才納入新的次數。權限、儲存與評分仍由後端逐次檢查。
- 新前端送答傳 `compact:true`，只省略固定題目文件；答案、解析、進度及葉片結果仍完整回傳。首次加入、接續及舊前端仍取得完整文件。
- 前端只在帳號世代、attempt、session、version 相符時沿用題目；不符則重新向後端接續，不擅自判定答案已存好。
- 揭答一次彙整答案，再依原本區塊順序產生解析；維持單題、題組及整卷的揭答時機。
- 看題不再先讀完整版本。作答鎖本人 attempt；加入與送答共用場次 advisory 的共享鎖，教師關場使用獨占鎖。取鎖後重讀場次，關場最長等候約一秒，逾時整筆失敗且可重試。
- 教室模式加入仍以獨占場次鎖保護 29 名學生上限；重複加入與重送仍靠既有唯一鍵及本人鎖序列化。
- 關場後拒收新答案；已存且相同 request_id 的重試仍可回看原紀錄。既有 Google 登入程式、權限、兩秒閱讀下限與同內容最多一葉不變。

## 本機比較方法

`automation/quiz-performance-bench.mjs` 啟動真正 PostgreSQL 17.6，只綁定 loopback，兩套資料庫使用相同種子題池與合成名冊。固定 max_connections=60、連線池=8、shared_buffers=64MB；這些是本機測試設定，沒有調整 Supabase 的正式設定。

使用已整理的 2,906 題、40 份合成預設卷與 180 份合成歷史自組卷；帳號、作答、試卷與權杖均為測試合成資料。22 人測試做三輪交錯 A/B，另外測 30 人；一半自組、一半同一份預設卷。每份 10 題、6 對4錯，逐題真等候 2.1 秒，不偽造防弊時間。測量端到端時間、連線池等候、資料庫交易時間、回應位元組、WAL 與錯誤。

「登入」僅模擬 Google OAuth 驗證完成之後，帶不同有效測試權杖進入學生資格與選卷流程；不壓測外部 Google／Supabase Auth，不能推論其尖峰容量。沒有模擬 Nano 的記憶體壓力、磁碟延遲、學校網路或主機故障。圖片流量另外以瀏覽器功能測試核對，不列入 DB 壓測。

發布門檻：答案與葉片一致、沒有多存／漏存、揭答不提前、權限與防弊全過；各輪 HTTP p95／max 與主要動作 p95 不得超過基準 10% 加 3ms 的本機雜訊容許值；DB 中位數不得退步、DB p95 同樣比較；送答回應至少下降 30%。不是只看整體平均。

## 初次測試發現與修正

第一版正確性全過，送答回應下降約 76%，但第三輪 HTTP p95 從85ms增為150ms，組卷尖峰也退步，沒有發布。

檢查程式發現逐卷 `LATERAL` 統計仍可能重複執行。改為先一次彙整本人作答、再連接可見試卷，重新執行完整 A/B。前一次數據保留在忽略目錄，沒有覆蓋或當作最終成績。

後續唯讀審查 `20261028-quiz-performance-audit-1793161268455` 確認測試應對齊 UI：先 `library_sessions` 核對資格，再 `pool_catalog`。早期同時送兩個請求的模型保留為額外壓力結果，兩批維持不通過。原先只在開始暖機，另補足每輪兩邊相同的完整 HTTP／連線池暖機；原門檻未放寬。加入 CPU、磁碟、`pg_stat_statements` 與 `EXPLAIN (ANALYZE, BUFFERS)`。

`actual-1`、`actual-2` 雖然整體 p95、資料量及所有正確性都改善，仍有單一回合的最大延遲超標，沒有部署。查詢剖析顯示候選排序查詢每卷跑10次，單卷約 91,885 次 shared buffer hits、117ms，沒有讀碟或 temp I/O。故再討論並實作上述本人次數快照；Claude 回合 `20261028-compose-performance-1793161962853` 同意。新增同一資料庫內舊／新函式各自 rollback 的深比：沒有紀錄、多次作答、舊題號、三難度、單元與錯題延伸，連選題順序都必須一致，12項相關測試通過後才重跑全班比較。若重跑仍退步就不部署，不為通過調整門檻。

## 最終本機比較

`actual-3/report.json`：三輪22人交錯 A/B 與30人測試通過；每版2,640個正式計入的請求，錯誤皆為0。30人的p95／max另由部署程式核對，與22人使用相同10%加3ms門檻。舊／新文件、題目順序、命名、答案、解析及配比逐項深比相同。

| 項目 | 優化前 | 優化後 |
|---|---:|---:|
| 全部回應資料量 | 22,578,832 bytes | 11,277,193 bytes |
| 送答回應資料量 | 14,899,897 bytes | 3,597,738 bytes（減75.9%） |

整體 DB 中位數下降28.9%，**未達30%目標**；符合事前共識中「安全全過、HTTP p95／max不退步、送答資料量明顯下降即可發布」的條件。SQL函式內實際組卷平均執行時間111.43→84.91ms，候選排序平均8.31→5.69ms；不是每個單次DB取樣都變快，例如組卷交易p95有波動，不將整體平均改善宣稱為所有單次請求的保證。

同人重送／加入競態只存一次；33人同時加入教室場次精確29人成功；太快送答不保存；匿名、教師、無名冊與跨年級拒絕；關場1,008.63ms後回可重試錯誤且保持open，成功關場後拒收新答案，原答案重送仍可回看。沒有為壓測停用防弊。

## 重跑方式與紀錄

先將優化前的四份 SQL 複製到忽略目錄中的 `baseline/supabase/`。勿把書商題庫、資料庫目錄、權杖、原始日誌或個別學生資料提交 Git。

```powershell
npm install --prefix tmp/quiz-bench-runtime --no-audit --no-fund embedded-postgres@17.6.0-beta.15 pg
node automation/quiz-performance-bench.mjs --baseline-dir <baseline/supabase> --output <ignored-output>
```

以 `QUIZ_BASELINE_SQL` 指向該次基準 `quiz.sql`，執行 `quiz-performance-equivalence.test.mjs` 可在同一資料庫內比對真實新舊函式的逐題結果。`quiz-compact.test.mjs` 驗證快照隔離與舊前端相容；`quiz-performance-migration.test.mjs` 驗證函式部署及既有資料保護。

正式 SQL 使用 `deploy-performance.mjs`：驗證專案、備份原函式、在單一交易內保護既有試卷／名稱／答案／葉片／進度／閱讀計時的摘要，只替換七個函式（含刪卷的資格捷徑與組卷統計）並重新載入 REST schema。沒有付費、升級、重啟或變更正式連線池。
