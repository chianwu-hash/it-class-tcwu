## 身分與資料契約

- `initGoogleCourseAuth()` 先啟用 `initNavbarAuth()`，再由受驗證 session 呼叫 `reconnect_grade3_progress()`。前端不能傳入來源座號、生日、email 或目標 user_id。
- 教師先對照第 02～05 週原始名冊核對歷史帳號、姓名與座號，填入 grade3_google_approvals；這張表不會自動用現行座號名冊填滿。伺服器核對已確認 email、115 年度名冊、有效身分卡名冊的班級座號／姓名，以及 `practice_account@apps.ntpc.edu.tw`。衝突、未知活動或無名冊均停止接回。
- 審查表分開保存目前 `student_code/display_name` 與歷史 `history_student_code/history_display_name`。轉班、換座號仍從原歷史代碼取成果，不把目前座號當作歷史本人證明。已綁定後異動會明確要求教師查核。
- 舊正式打字紀錄若為完成、關數等於總關數但沒有分數，僅在教師核對完整原始 JSON 後補為滿分；其他空分數的已驗證未完成列補為已過關數。來源身分卡完成列缺分數、空姓名／關數、矛盾完成旗標均拒絕，不能造出成果。
- 整個人的歷史成果在同一交易接回。學生代碼的交易鎖與唯一綁定防止重複領取；保留 `guest_progress` 原資料及 `grade3_google_imports` JSON 快照。綁定完成後重登入不再匯入，因此教師重設正式進度不會復活。
- SQL 部署即凍結本課程所有舊匿名寫入，沒有分班漸進模式。須在全六班可切換時一起發布，避免新舊版本交錯使用；其他課程不受凍結影響。
- `createGoogleCourseProgress()` 經受控本人 RPC 載入／保存正式進度，伺服器取較高成果、不相加；遷移前既有正式列必須有教師核對的完整 JSON 快照，否則整人停止接回；保存失敗不解鎖下一關。名冊異動後停止寫入，帳號變更立即鎖住並重載。
- 共用 typing 新增 opt-in `progressAdapter`，由外部本人控制器負責鎖定與 navbar；沿用原驗答、逐關解鎖、動畫及失敗重試。舊 `guestProgress`、其他年級與學期的預設行為不變。此分支不提供學生自行重設，教師沿既有後台重設正式進度。
- 第 02～05 週採相同轉接 API，保留原活動與解鎖條件，第 05 週本人帳號從可信 RPC 回應取得，不再呼叫生日驗證 RPC。
- 後台本課程只列正式 Google 成果，歷史來源保留在資料庫，不雙列、不重設歷史。尚未登入者的來源成果將在首次正確登入時接回。
- 努力樹使用共同 `/my-tree.html?course=grade3-115-1`，先接回再讀正式成果。不得退回無課程欄位的跨學期資料。換帳號／課程時清掉舊樹；讀取失敗不保留上一人的成果。

## 驗證與發布次序

本機測試：`node --test automation/tests/grade3-google-transition.test.mjs`。首次在忽略的測試目錄安裝 `npm install --prefix tmp/week06-dbtest @electric-sql/pglite --no-save --package-lock=false`。使用真正 PostgreSQL 引擎與合成帳號／名冊，測 RLS、錯帳號、快照、重試、凍結、其他課程、進度合併、重設及名冊異動。PGlite 單連線測試不取代正式雙連線並行驗證。

瀏覽器：`automation/tests/grade3-week06-browser.cjs` 須以有效 AI 工作瀏覽器 LeaseId／CdpUrl 環境變數執行。只攔截本機 auth 模組，使用合成身分和 RPC 回應，沒有登入真實學生或寫正式資料。驗證五關保存、保存失敗停留、錯字提示、navbar 重渲事件、匿名與接回失敗鎖定、四葉一花、舊六關五葉一花、舊週入口及本人帳號、390／1280 無水平溢出。

發布前必須完成：

1. 以受授權教師帳號查核正式 schema、名冊與帳號對應；執行配套 preflight，確認未知活動、無效來源及未解決身分衝突為零，並保留受限備份。歷史座號差異及既有正式列數可以非零，但必須逐人完成歷史身分／完整原列快照審查。第 05 週目前為六關，需特別核對正式歷史版本是否曾有五關，不能直接換算。
2. 參照 grade3_google_approve_roster.sql 核對並準備各人的歷史身分審查；座號異動或同名者先人工處理。綁定後異動須保存原綁定與兩邊進度，由教師／DB 管理者另審查修復，學生不可自行重新綁定。不得刪除成果讓檢核通過。教師示範使用經授權的測試學生帳號，教師帳號不例外認領。審查與部署 `supabase/grade3_google_transition.sql`，凍結後填入已核對身分；確認審查表完整，再同步發布全部相關前端。SQL 保留來源，不能用刪除資料方式回復；若需回復先凍結活動並保留新成果，另審查修復方案。
3. 用受授權代表學生驗證 OAuth 回原頁、本人舊成果、舊週補做、登出換人、後台重設與樹同步、雙分頁接回。核對實際學生電腦首次 Google 開通畫面。
4. 教師後台切換 06 隱藏／顯示並恢復預定狀態。正式驗證完成後才能把教案標記為可上課。

## 維修與審查結果

座號異動保留原 user_id、歷史代碼、匯入稽核及正式進度，由 DB 管理者核對後同一交易更新目前名冊、審查及綁定。不要刪綁定重匯；若誤刪，從備份核對並還原原綁定。匯入稽核殘留會明確拒絕重匯，已正規化的正式列也不能拿舊快照重新審查。

無效來源已凍結時，先暫停活動、保存受限備份，再另擬逐人維修交易；DB 管理者取得來源表寫入鎖，只暫停指定凍結 trigger，修正後恢復並重跑 preflight 才提交。已接回者修正式成果，不重新匯入來源。詳見 SQL 審查範本的註解，本次沒有執行任何維修或正式操作。

Claude 唯讀審查與修正紀錄：[第 06 週審查紀錄](grade3-week06-review.md)。審查有明列覆蓋缺口，不能當作真實 OAuth／正式名冊驗收。最後合成 SQL 測試包含十二種無效來源、座號異動訊息順序、23505 殘留匯入衝突、教師重設與稽核權限。來源正式 schema 的關數與完成欄位原有 NOT NULL；轉換仍增加顯式空值防護，以免不同部署版本放行。
